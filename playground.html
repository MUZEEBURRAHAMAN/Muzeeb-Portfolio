CLAUDE SKILLS & AUTOMATION

Turning repeatable design thinking into reusable workflows

I started building Claude Skills when I noticed I was repeatedly giving AI the same context, frameworks, and instructions. Instead of recreating the workflow every time, I turned the processes I trusted into reusable tools that run directly inside Claude Code.

01 · The Problem
Good AI output depends heavily on the workflow around it.

Without a structured rule system, designers get trapped in continuous prompting friction:

Explain Context → Prompt → Token Drift → Manual Fix → Re-prompt → Review

I wanted a consistent, predictable, and automated starting point for any session.

02 · The Architecture
~ from repeated friction to packaged agent tool ~
01 · PATTERN
Identify Friction

Notice prompting loops repeated >3 times across reviews and design handoffs.

Trigger: Prompt Fatigue
02 · ENCODE
Formalize Rules

Define structured W3C tokens, WCAG 2.2 rules, checklists & edge matrices.

Ruleset: Markdown & XML
03 · PACKAGE
Package as .skill

Bundle heuristics into a distributable Claude Code asset ready to execute.

Output: Reusable .skill
Zero prompt re-explaining required on any new session!

DESIGN TOKENS & ARCHITECTURE

Making design decisions reusable across platforms

Hardcoded hex values and arbitrary pixel margins create systemic brand drift. I engineer multi-tier token architectures following W3C Design Token Community Group (DTCG) standards to ensure design decisions compile flawlessly into CSS, iOS, and Android.

The 3-Tier Token Architecture
TIER 01 · GLOBAL PRIMITIVES blue.600 = #0284c7

Raw, context-agnostic values. Color ramps, modular scale type sizes, and baseline grid multiples.

TIER 02 · SEMANTIC & CONTEXTUAL color.action.primary = token(blue.600)

Intent-driven tokens that change dynamically depending on active theme (Dark Mode / High Contrast).

TIER 03 · COMPONENT SCOPED button.primary.bg = token(color.action.primary)

Strictly isolated bindings protecting components from unintentional global side-effects.

COMPONENT ARCHITECTURES

Designing for consistency and resilience at scale

A design system is only as robust as its edge cases. I design components with mandatory 7-state coverage, keyboard accessibility traps prevention, and ARIA compliant semantics before developer handoff.

The 7-State Resilience Matrix
✓ Complete State Coverage Standard
01 · Default 02 · Hover 03 · Active / Pressed 04 · Focus-Visible (Keyboard) 05 · Disabled 06 · Error / Invalid 07 · Loading / Pending
Enterprise Principle: If a component doesn't define its loading, error, and keyboard focus states, it is only 40% designed.
