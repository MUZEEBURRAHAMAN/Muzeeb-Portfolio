Overview

I built the QA teammate I didn't have.

I was the only designer across five legal-tech products at Omnis AI. Before each release I checked every screen by hand, and it took hours. So I built a tool that does the checking, and I keep the final say.

02
The problem

Design bugs hide behind clicks.

A screen can pass review when it first loads. The problems show up after someone opens a dropdown, submits a form with an error, or lands on an empty page.

Nobody had time to click through all of those states before each release, so those bugs reached real users.

I needed a way to check every state of every screen, fast enough to run before each release, and accurate enough that engineers would trust it.

05
Design process

Two versions. The first one made things up.

Each version tested the same question: can a tool find design problems that engineers trust enough to fix?

V1Reading screenshots with AI

What I built
The tool took screenshots and asked an AI vision model to list problems, each with a location, a severity, and a suggested fix.
What I saw
On a dashboard I knew well, it reported low contrast on "the secondary button beside the search field." That button didn't exist. The AI had guessed from what dashboards usually look like.
Insight
If one finding is made up, you have to double-check all of them, and that cancels out the time saved.

FinalChecking the real page, with proof

What I built
The tool works inside a live browser. It runs 229 fixed rules first and uses AI only for layout questions. Any problem that can't point to a real element on the page gets thrown out.
What I saw
Over 90% of findings point to an exact element in the page code, so an engineer can find each problem in one click.
Insight
A short list people trust beats a long list they have to verify.
Keep or dropHow each finding earns its place in the report
A rule or the AI spots a problem
Does it point to a real element on the page?
Yes: it goes in the report
No: it gets dropped
If a designer rejects a finding, the tool remembers and won't flag it again

07
Design decisions

Proof first, clicks before judging, fixes ready to paste.

  1. Proof before opinion.

    Fixed rules handle what can be measured: contrast, accessibility attributes, and design tokens. AI handles judgment calls, and only when it can point to the element.

  2. Click before judging.

    The tool opens each dialog, dropdown, drawer, and tab before it reviews a screen.

  1. Every problem comes with its fix.

    Each card shows a severity, the rule it broke, a plain-English title, the design principle behind it, a copy-paste CSS fix, and a confidence score.

  1. Each role sees its own list.

    One run, six readers, each filtered to the work they can act on:

    • Product designer: problems by severity and token mismatches. Rejecting a false alarm stops it coming back.
    • Frontend developer: blockers with the exact element, its styles, and the fix.
    • QA: a log of every dialog, drawer, and dropdown the tool opened.
    • Content designer: a separate list of confusing labels and copy.
    • Engineering manager: a dashboard across all products.
    • Leadership: a record of problems fixed over time.

10
Looking back

What building it taught me.

  • Trust comes before speed. A tool that reports 50 problems with 15 made up costs more time than checking by hand.
  • Real checks need clicks. Looking only at first loads misses overflowing dropdowns, error messages, and empty pages.
  • Engineers fix what they can paste. A selector and a code fix get merged. A vague comment gets skipped.
Where it standsA working prototype with 187 automated tests and about 27,000 lines of TypeScript. After a company restructuring changed the staging setup, I parked it. Testing at a larger scale is still open.
If I pick it back up
  1. Remember a starting point for each product, so later runs flag only new problems.
  2. Run on every staging deploy through GitHub Actions and flag new blockers on pull requests.
  3. Re-check after a fix is merged to confirm it worked.
  4. Send verified notes back into Figma files through the Figma API.
11
Questions

Questions people ask.

Who approved giving a product designer live credentials to staging environments?
No new grant was needed: it reused the same staging access I already held as the product designer auditing those apps by hand. The engine logs in with my credentials, scoped to the same environments I already reviewed, and never touched production or anyone else's access.
Are you a designer or an engineer?
Product design is my core foundation: research, UX architecture, interaction design, and design systems. I also write production TypeScript to ship working prototypes and developer tooling end-to-end.
What was your contribution compared to engineering?
I conceived, designed, and built the entire engine myself, covering the MCP architecture, Playwright crawlers, axe integrations, and Next.js reporting dashboard.
How do you prevent model hallucinations?
Deterministic checks evaluate objective rules (contrast math, aria attributes). AI heuristic findings are rejected unless they map to a valid DOM node and pass structured false-positive validation.
How does this differ from axe-core or Lighthouse?
Lighthouse and axe evaluate a single static URL. This engine authenticates, crawls interactive application states, pairs axe-core with semantic layout heuristics, and exports diff-ready CSS token patches.
How did you measure audit effectiveness?
By tracking verified findings per screen and measuring false-positive rates against real product staging environments.
Can this deploy to production CI pipelines?
Not yet. Running audits on every staging deploy and flagging new blockers on pull requests is the next step listed above.
